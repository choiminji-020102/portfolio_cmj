# 풀버전 (9단 구조)

## ① 배포 환경에서 벡터 DB 생성 실패 & 매 요청 재로딩 성능 저하 · ⭐⭐⭐⭐⭐

**문제 상황** · 로컬에선 잘 되던 RAG 챗봇이 배포 서버에서 Chroma 벡터 DB 생성 단계에서 실패했다. 동시에, DB가 있어도 질문마다 벡터 DB를 통째로 다시 로딩해 응답이 느렸다.

**원인 분석** · 두 가지가 겹쳐 있었다.
1. `persist_dir` 기본값이 `"/RAG/chroma"` — 앞에 `/`가 붙은 절대경로(파일시스템 루트)였다. 로컬에선 우연히 통했지만, 배포 서버에선 루트에 쓰기 권한이 없어 DB 생성이 실패했다.
2. 함수 진입 시 `_vectordb = None`을 매번 실행 → 인메모리 캐시를 스스로 무력화하고 있었다. 그래서 캐시 분기가 있어도 항상 재로딩됐다.

**기존 구조의 한계** · 경로가 실행 환경에 종속적이었고, 예외 처리가 없어 실패 시 원인 파악이 어려웠으며(빈 문서·경로 없음도 그냥 통과), 캐시 로직이 있으나 마나였다.

**해결 방법 비교** · (a) 절대경로를 환경변수로 주입 vs (b) 프로젝트 기준 상대경로로 통일. 배포 파이프라인 단순성·이식성을 위해 (b)를 택했다.

**구현 / 핵심 코드**
```python
# before
def build_or_load_vectordb(source_folder, persist_dir="/RAG/chroma"):  # 절대경로 → 배포 실패
    global _vectordb
    _vectordb = None                                                    # 캐시 매번 초기화
    ...
# after
def build_or_load_vectordb(source_folder, persist_dir="RAG/chroma"):    # 상대경로로 이식성 확보
    global _vectordb
    # _vectordb = None  # 캐시 재로딩 필요할 때만 주석 해제                 # 인메모리 캐시 복원
    if _vectordb:
        return _vectordb
    try:
        if not os.path.exists(source_folder):
            raise FileNotFoundError(...)     # 경로 없음 방어
        raw_documents = extract_texts_from_folder(source_folder)
        if len(raw_documents) == 0:
            raise ValueError("문서가 비어 있음")   # 빈 DB 생성 방지
        ...
    except Exception as e:
        print(f"❌ 벡터 DB 로드/생성 중 오류: {e}"); raise
```

**적용 후 개선점** · 로컬·배포 동일 경로로 동작(이식성 확보), 인메모리 캐시가 살아나 첫 요청 이후 재로딩 제거(응답 지연·임베딩 비용 감소), 방어 코드로 실패 원인 즉시 식별.

**배운 점** · 로컬에서 되던 코드가 배포에서 깨지는 전형이 경로·권한 가정이라는 것, 그리고 "있는 캐시"와 "동작하는 캐시"는 다르다는 것 — 성능 문제는 코드를 한 줄 지우는 게 아니라 왜 캐시가 안 타는지를 봐야 한다는 걸 배웠다.

## ② 질문 라우팅 아키텍처 설계 — 4-way 분류 + 노드 역할 재정의 · ⭐⭐⭐⭐⭐

**문제 상황** · 초기엔 모든 질문을 하나의 응답 생성기로 보냈다. 그러다 보니 (a) 낙농과 무관한 질문("로또 번호 알려줘")에도 GPT가 성실히 답해 챗봇 정체성이 흐려지고, (b) "103번 소 상태 어때?" 같은 개체 조회와 "발정 시기 언제야?" 같은 일반 지식을 같은 경로로 처리해 답변 품질이 들쭉날쭉했다.

**원인 분석** · 질문의 *의도(intent)*를 먼저 구분하지 않고 곧장 답을 생성한 게 근본 원인이었다. 의도별로 필요한 데이터 소스(사내 문서 / 농장 DB / 대화 맥락)가 전혀 다른데 한 경로로 뭉뚱그린 것.

**기존 구조의 한계** · 무관 질문 차단 불가, 개체 조회와 지식 질문의 혼선, 그리고 "너 아까 뭐랬어?" 같은 챗봇 UX 대화를 담을 자리가 없었다.

**여러 해결 방법 비교**
- *프롬프트 하나로 다 처리* — 구현은 쉽지만 의도별 데이터 소스 분기가 불가능.
- *LangGraph 조건부 분기(채택)* — classifier 노드가 의도를 4종으로 분류하고, `add_conditional_edges`로 전용 노드에 라우팅. 유지보수·확장에 유리.

**왜 이 방식인가** · 의도별로 데이터 소스가 다르므로 분류를 독립 단계로 분리하는 게 정석이고, 노드 단위라 이후 기능 추가(새 의도)도 엣지만 늘리면 됐다.

**구현 / 핵심 코드**
```python
# classifier가 4종으로 분류 → 전용 노드로 라우팅
builder.add_conditional_edges("classifier", route_by_answer_type, {
    "rag":        "rag_response",     # 낙농 일반 지식 → 사내 문서 RAG
    "cow_info":   "cow_info_graph",   # 특정 개체("103번 소","그 소") → 농장 DB 서브그래프
    "general":    "general_response", # 인사·감정·"이전 질문 뭐였지?" → UX 대화
    "irrelevant": "irrelevant_response", # 완전 무관 → 정중히 거부
})
# LLM이 엉뚱한 라벨을 뱉어도 방어
if result not in {"rag", "cow_info", "general", "irrelevant"}:
    result = "irrelevant"
```
`general` 노드는 단순 잡담용이 아니라 "이전 질문 뭐였지?" 같은 UX 흐름 전담으로 역할을 재정의했고, `cow_info`는 "그 소·그 아이" 같은 지시어까지 개체 조회로 흡수하도록 분류 기준을 세웠다.

**적용 후 개선점** · 무관 질문을 LLM 호출 전에 차단(토큰 낭비 제거), 의도별 최적 데이터 소스 연결로 답변 품질 안정화, LLM 오출력에도 안전한 fallback 확보.

**배운 점** · LLM 앱의 품질은 프롬프트 하나를 잘 쓰는 게 아니라 의도를 먼저 라우팅하는 아키텍처에서 갈린다는 것, 그리고 LLM 출력은 항상 예외가 있으니 분류기에도 방어 코드가 필요하다는 걸 배웠다.

## ③ RAG 검색 실패 시 응답 전략 — "프롬프트냐 노드냐" 설계 의사결정 · ⭐⭐⭐⭐⭐

**문제 상황** · 사내 문서를 검색해 답하는 RAG 구조에서, 문서에 관련 내용이 없을 때 어떻게 응답할지가 정의돼 있지 않아 답변이 비거나 흐름이 끊겼다.

**원인 분석** · "문서 기반 답변"만 상정하고 검색 실패(no-hit) 케이스를 설계에 넣지 않았다.

**기존 구조의 한계** · 검색 결과가 비면 빈 context가 그대로 프롬프트에 들어가 부실한 답이 나가거나, 사용자가 아무 응답도 못 받았다.

**여러 해결 방법 비교**

| 항목 | 프롬프트 내부 처리 | LangGraph 노드 분기 |
|---|---|---|
| 응답 속도 | 빠름(한 번에 처리) | 느림(재분기 필요) |
| 유지보수 | 쉬움 | 복잡 |
| 의도 제어 | 정확("없으면 지식으로 답") | 흐름 중첩 위험 |
| 구현 난이도 | 낮음 | 높음(상태 추가 전달) |

**왜 이 방식인가** · 속도·유지보수·의도 제어 세 축에서 모두 프롬프트 처리가 우위였고, no-hit는 별도 노드를 만들 만큼 복잡한 분기가 아니라 한 프롬프트 안에서 조건부 지시로 충분하다고 판단했다.

**구현 / 핵심 코드**
```python
# 검색 결과가 없으면 안내 문구로 대체 → 프롬프트가 no-hit를 인지
context = context.strip() or "※ 참고할 문서가 없습니다."

template = """
아래 참고 자료를 우선적으로 사용해서 답변하세요.
만약 참고 자료가 비어있거나 참고자료에서 답을 찾을 수 없다면,
당신이 알고 있는 지식이나 상식, 경험을 바탕으로 대신 답해도 괜찮습니다.
[참고 자료]
{context}
"""
```
더해 `similarity_search_with_score`로 유사도 점수를 context에 함께 실어, 모델이 자료의 신뢰도를 참고해 "문서 기반"과 "지식 기반"을 스스로 저울질하도록 했다.

**적용 후 개선점** · 검색 실패에도 끊김 없는 graceful fallback 확보, 별도 분기 노드 없이 그래프 단순 유지, 유사도 점수로 답변 근거의 투명성 향상.

**배운 점** · RAG의 완성도는 "잘 찾을 때"가 아니라 "못 찾을 때 어떻게 행동하는가"에서 드러난다는 것, 그리고 모든 예외를 노드로 쪼개는 게 능사가 아니라 비용 대비 효과로 처리 위치를 고르는 판단이 설계라는 걸 배웠다.

## ④ 사용자별·채팅방별 세션 메모리 구조 설계 · ⭐⭐⭐⭐

**문제 상황** · 여러 사용자가 동시에, 또 한 사용자가 여러 채팅방을 오가며 챗봇을 쓰는데, 대화 맥락이 서로 섞이면 안 됐다.

**원인 분석** · 대화 기록을 담을 저장 단위(세션 키)와 저장 포맷을 정하는 게 관건이었다. 전역 단일 저장소로는 유저·채팅방을 구분할 수 없다.

**기존 구조의 한계** · (메모 기준) 초기엔 기록을 `{"질문":…, "답변":…}` dict로 누적했는데, 이를 프롬프트에 직렬화하면 LLM이 대화 흐름으로 인식하기 어렵고 LangChain 표준 메모리와 호환도 나빴다.

**여러 해결 방법 비교** · 세션 키를 (a) `user_id` 단일 vs (b) `(user_id, chat_id)` 튜플. 한 유저가 방을 여러 개 쓰므로 (b)를 택했다. 저장 포맷은 dict vs 화자 접두 문자열 리스트를 비교해 후자를 택했다.

**구현 / 핵심 코드**
```python
# (user_id, chat_id) 튜플을 키로 세션 격리
chat_memory_store: Dict[Tuple[str, str], List[str]] = {}

def get_chat_memory(user_id, chat_id) -> List[str]:
    return chat_memory_store.get((user_id, chat_id), [])  # 없으면 KeyError 대신 빈 리스트

def append_chat_memory(user_id, chat_id, question, answer):
    key = (user_id, chat_id)
    memory = chat_memory_store.get(key, [])
    memory.append(f"사용자: {question}")   # dict가 아닌 화자 접두 문자열
    memory.append(f"소담이: {answer}")
    chat_memory_store[key] = memory
```
이 문자열 리스트를 `"\n".join()`으로 이어 프롬프트에 넣으면 실제 대화 스크립트 형태가 돼, "그 소·아까 그거" 같은 후속 질문(멀티턴)의 맥락도 자연스럽게 이어졌다.

**적용 후 개선점** · 유저·채팅방별 맥락 완전 격리, `.get(key, [])`로 신규 세션 안전 시작(KeyError 제거), 대화 스크립트형 포맷으로 멀티턴 이해도 향상 및 LangChain 표준 메모리 이관 호환성 확보.

**배운 점** · 대화형 AI에서 "메모리를 어떤 자료구조와 키로 들고 있느냐"가 멀티턴 품질과 확장성을 좌우한다는 것, 그리고 LLM에겐 dict보다 사람이 읽는 대화 텍스트 포맷이 더 잘 먹힌다는 걸 배웠다.

## ⑤ RAG 출처 표기 반복 개선 — 신뢰성 있는 응답 포맷 다듬기 · ⭐⭐⭐⭐

**문제 상황** · RAG 답변에 근거 문서 출처를 붙이기 시작했는데, 출처 표기에서 자잘한 오류가 연쇄적으로 터졌다. 파일 확장자가 그대로 노출되고, 같은 문서가 중복 표기되고, `**` 같은 마크다운 기호가 날것으로 나가고, 영어 질문에도 "출처:"라고 한글로 붙었다.

**원인 분석** · 출처 문자열을 만드는 단계에서 (a) 파일명 정규화, (b) 중복 제거, (c) 출력 포맷(기호·언어) 규칙이 정리돼 있지 않았다. 사용자에게 보이는 최종 텍스트 품질을 초기엔 과소평가했다.

**기존 구조의 한계** · 출처가 `무언가.pdf`처럼 노출되고 중복·기호가 섞여, 근거를 보여주려던 기능이 오히려 지저분해 보였다.

**해결 / 구현** · 문서 임베딩 시점부터 확장자를 제거한 파일명만 metadata에 저장하고, 출처는 중복 제거 후 쉼표로 구분, 특수기호 제거, 그리고 질문 언어에 맞춰 `[출처: …]` / `[Source: …]`로 분기하도록 프롬프트 규칙과 파이프라인을 다듬었다. (커밋 `c2f4e1a`→`5961f94`→`83f0337`→`b945b5a`→`5d29b8a`로 이어진 반복 개선)

**핵심 코드**
```python
# 임베딩 단계에서 확장자 제거한 파일명만 metadata로 저장
base_name = os.path.splitext(file_name)[0]
documents.append(Document(page_content=chunk, metadata={"source": base_name}))

# 프롬프트 출력 규칙: 언어 분기 + 중복 제거 + 기호 제거
"""
- 모든 답변은 *, -, • 등 특수 기호 없이 일반 문장으로 작성
- 답변 아래 줄에 출처를 반드시 포함
  → 한글 질문: [출처: 파일명1, 파일명2]  → 영어 질문: [Source: filename1, filename2]
  → 파일명은 중복 없이 쉼표로 구분
"""
```

**적용 후 개선점** · 출처가 깔끔한 파일명으로, 중복·기호 없이, 질문 언어에 맞춰 표기돼 답변의 신뢰성과 가독성이 함께 올라갔다.

**배운 점** · RAG에서 "근거를 보여주는 것"과 "보기 좋게 보여주는 것"은 별개이며, 사용자에게 닿는 마지막 한 줄까지 다듬는 게 제품 완성도라는 걸 배웠다. 한 번에 끝나지 않고 여러 커밋에 걸쳐 관측→수정을 반복한 과정 자체가 실무의 모습이었다.

# 슬림버전 (카드용)

## ① 배포 환경 벡터 DB 생성 실패 & 재로딩 성능 저하 · ⭐⭐⭐⭐⭐
- **문제** — 로컬에선 되던 RAG가 배포 서버에서 Chroma DB 생성 실패, DB가 있어도 매 요청마다 재로딩돼 느림
- **해결** — 절대경로 `/RAG/chroma` → 상대경로로 이식성 확보, `_vectordb=None` 제거로 인메모리 캐시 복원, 예외·빈문서 방어 추가
- **효과** — 로컬·배포 동일 동작, 첫 요청 이후 재로딩 제거로 지연·임베딩 비용 감소
- `#배포환경` `#성능` `#캐시`

## ② 질문 라우팅 아키텍처 설계 · ⭐⭐⭐⭐⭐
- **문제** — 모든 질문을 한 경로로 처리 → 무관 질문 차단 불가, 개체 조회와 일반 지식이 뒤섞여 품질 불안정
- **해결** — classifier가 의도를 4종(rag·cow_info·general·irrelevant)으로 분류, LangGraph 조건부 분기로 전용 노드 라우팅 + LLM 오출력 방어
- **효과** — 무관 질문 LLM 호출 전 차단, 의도별 최적 데이터 소스 연결로 답변 품질 안정화
- `#LangGraph` `#아키텍처` `#의도분류`

## ③ RAG 검색 실패 시 응답 전략 (설계 의사결정) · ⭐⭐⭐⭐⭐
- **문제** — 문서에서 답을 못 찾는 no-hit 케이스가 설계에 없어 답변이 비거나 흐름이 끊김
- **해결** — '프롬프트 처리 vs 노드 분기'를 속도·유지보수·의도제어로 비교 → 프롬프트 fallback 채택("자료 없으면 지식 기반 답변")
- **효과** — 검색 실패에도 끊김 없는 응답, 그래프 단순 유지, 유사도 점수로 근거 투명성 확보
- `#RAG` `#Fallback` `#의사결정`

## ④ 사용자별·채팅방별 세션 메모리 구조 · ⭐⭐⭐⭐
- **문제** — 전역 단일 메모리로 유저·채팅방 대화가 섞임, dict 저장은 LLM 이해·LangChain 호환 모두 불리
- **해결** — `(user_id, chat_id)` 튜플 키로 세션 격리 + `.get(key, [])` 안전 조회, 저장 포맷을 화자 접두 문자열 리스트로 전환
- **효과** — 맥락 완전 격리·KeyError 제거, 대화 스크립트형 포맷으로 멀티턴 이해도·이관 호환성 향상
- `#Memory` `#멀티턴` `#세션관리`

## ⑤ RAG 출처 표기 반복 개선 · ⭐⭐⭐⭐
- **문제** — 출처에 확장자 노출·중복·마크다운 기호 노출, 영어 질문에도 한글 "출처:" 표기
- **해결** — 임베딩 단계에서 확장자 제거 파일명만 metadata 저장, 중복·기호 제거 + 질문 언어별 `[출처]`/`[Source]` 분기 (커밋 5건 반복 개선)
- **효과** — 근거 출처가 깔끔·정확·다국어로 표기돼 답변 신뢰성과 가독성 동반 상승
- `#RAG` `#응답품질` `#다국어`
